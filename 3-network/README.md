## 流量路径

现代网络请求自上而下分层处理：应用层（程序传输的内容）→ 传输层（TCP/UDP，分段与端口）→ 网络层（IP 寻址与路由）→ 链路层（网卡收发）。代理工作在哪一层，决定它能接管哪些流量，也决定 WSL 侧要不要单独配置。

代理按工作层次分两类，先确认你用的是哪一类：

- **工作在网络层（TUN / 虚拟网卡）**——如 Amnezia、Clash 的 TUN 模式。它在 Windows 上创建一块虚拟网卡（TUN/L3 设备），把系统默认路由指向它，因此整机所有 IP 流量都经此进入隧道，无需各程序单独配置。WSL2 运行在镜像（mirrored）模式，与 Windows 共用网卡和路由表，流量出 Windows 时同样全部进该隧道——**这种情况下 WSL 侧无需任何代理配置**。
- **工作在应用层（系统代理 HTTP/SOCKS）**——如未开 TUN 的 Clash / Clash Verge。只接管显式配了代理的程序，未配置的仍走直连。**这种情况下 WSL 需要自己配**：apt 代理、环境变量、DNS，见 [wsl-network.md](./wsl-network.md)。

### 作者的实际配置（示例，非要求）

下面是本仓库作者这台机器的实况，仅供参考——它是上面「网络层」那一类的一个具体例子，不是你必须照做的配置。

- **桌面端**：Amnezia 全局 TUN，出口 AWS 东京。
- **WSL 侧**：因走网络层 TUN，零配置；原先指向 Clash `127.0.0.1:7897` 的 SSH ProxyCommand 已在 `~/.ssh/config` 注释停用。
- **隧道指标**：到 GitHub 的 RTT 稳定约 60 ms、丢包接近 0%，隧道 MTU 1320。

隧道的代价是延迟和上行带宽：上行慢于下行，push 较大内容偏慢是隧道天性，不是 git 故障。下面是作者 2026-06 分时段多轮实测的范围（测量落点不同、结果差异很大，故标注路径），仅供「慢到什么程度算正常」的参照：

- 下行（到 GitHub 全程）：约 3–9 MB/s，多数在 5–6。
- 上行（到 GitHub，真实 git push 实测）：传输阶段约 1.4–3.4 MiB/s；一次约 10 MB 的 push 计入握手与压缩开销后，有效速率约 0.9–1.5 MB/s。
- 参照（仅测「作者机器→东京」接入段，落点为 Cloudflare 东京边缘，与 AWS 出口同城）：下行约 16 MB/s 很稳、上行约 1.5–4.6 MB/s——可见作者侧接入不是瓶颈，限制来自隧道本身与上下行的天然不对称。

结论：下行快于上行（约 2–4×）。常规改动推送为秒级；上传较大的新增内容（git push 的 pack 走上行）受上行速率制约会变慢，且单次 push 还要摊握手/压缩开销——这是隧道特性，非 git 或网络故障。
